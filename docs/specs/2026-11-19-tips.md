Builds `docs/guidance/03-tips.md` (what the user sees, rules, catalogue, texts, tests). This file
only records what differs from that plan, the data shape, the modules and the order of work.
Status: **agreed by the owner 2026-11-19**: decision 7 confirmed; session A first; the dates tips
need are real data, and tip history syncs through Drive (this replaces decision 5 for tips).

## Changes to the plan

- **History syncs.** The `tips` preference is also a section of the Drive sync file, merged
  like other synced data, so a × or Not now on one device holds on the others.
- **`statusSince`** on activities and goals: the day the status last changed, stamped at save
  time beside `updatedAt` (every way of changing a status goes through save). Absent on old
  items: tips read the day of `updatedAt`, then `createdAt`, as "since" (later than the truth,
  so a tip fires late, never early). Used by `stuck-step` (In progress since) and `waiting`
  (the blocker To do since). Feature 13's `doneAt`/`achievedAt` stay its own; nothing here
  uses or blocks them.
- **`goal-unfinished`** (from `06-goal-form`, class B, cooldown 30 days) joins the catalogue.
- **Look** (owner, 2026-11-19): tips are yellow (`--tip`, a lamp yellow lighter than Purpose's
  gold; the word "Tip" in `--tip-ink`, a dark amber, for contrast) and carry a light-bulb icon.
  Purple was dropped: it is the colour of States.
- **Session B gains** (owner, 2026-11-19): "Show me another tip", easy to reach at any time, so a
  user can ask for tips about the app and their plan when they are open to them. To design: where
  it lives (the card, the Guide's Start here, or both), and how asked-for tips sit beside the
  one-a-day tip and the history (likely: asked-for tips do not count toward the 3 showings).
- Session B: views and days recorded whenever tips are on; `seen` gains `menu`, `templates`;
  `halfway` records "was under 40 %" in `tips.since`; decide then whether `seen` syncs too.

## Data shape

- Preference `tips` (per user; synced):
  `{ off?: boolean, day?: ISODate, current?: string | null, shown: { [key]: { n, last, closed?, snoozed? } }, since: { [fact]: ISODate } }`.
  Missing or broken reads as defaults (`off` false, empty maps). Saves merge with what is
  stored (`closed` and the larger `n` win), so a second tab never undoes a ×.
  `since` keys: `doing:<activityId>`, `waiting:<activityId>`, `achieved:<goalId>`,
  `under40:<goalId>`; dropped when the fact stops being true or the item is gone.
- Preference `seen` gains `menu?: true`, `templates?: true`. Unknown facts kept as today.
- Sync file: optional top-level `tips` (same shape). Read with `readTips`, merged with
  `mergeTips`: per key the larger `n`, the later `last` and `snoozed`, `closed` if either; `off`
  and `day`/`current` from the copy with the later `day`; `since` the earlier date per fact.
  An older version drops the section when it rewrites the file; each device still holds its own
  copy and writes it back on its next sync, so nothing is lost for good. Backups carry it as they
  carry the sync format; restoring ignores it.
- Items: optional `statusSince` (activities, goals). Old versions keep it as they keep any item
  field; an edit made in an old version leaves it stale until the next status change.
- Fixtures: the old fixtures must still load and save unchanged. Opening them now records the tip
  of the day (a new key the old code could not write), so `scripts/fixtures.mjs` leaves the
  `tips` preference and the sync file's `tips` out of the comparison when the fixture has none
  (`NEW_KEYS`); everything else must match exactly. The round trip of the section is proven by
  unit tests (`drive.test.ts`, `merge.test.ts`, `tip-history.test.ts`).
- `statusSince` is left out when the app itself starts an activity on its start date
  (`autoStarted` already says since when), so old plans save unchanged.

## Session B: what was decided while building (2026-11-19)

- **`seen` stays per device.** Tip history already syncs, so a once-only tip shown on one device
  is not shown on the other. Only the facts that trigger a tip (Map opened, menu used, templates
  opened, days opened) are per device, so a device may offer a discovery tip a little later.
- **Days and views** are recorded on every draw while tips are on, in a plan that is not a sample
  (as before, also while Getting started is on). Getting started's "views" task may therefore
  tick the moment it is started, if Map, Timeline and Graphs were opened before; that is true.
- **`halfway`** reads `since['under40:<goalId>']`, written when the tip of the day is chosen
  (once a day) for every active goal under 40 %; dropped when the goal is gone or not active.
  A goal that passes 40 % on the day it is made is never praised: late or never, not wrong.
- **`achieved`** reads `statusSince` only (no `since` key): an old goal without the stamp is never
  called "just reached".
- **Ask for a tip** (owner's request). *Another tip* on the card, and *Show me a tip* as the
  action of the Guide article `tips-all` (it opens the Overview). An asked-for tip:
  - is any tip whose condition is true now, in the usual order, skipping the tip of the day and
    those already asked for since the page was opened; cooldowns, the 3 showings, Not now, the
    quiet first days, a sample plan and Getting started do not apply (it was asked for); × does;
    the conditions themselves (class D's 5 days among them) do;
  - is not recorded (no `n`, no `last`); × and Not now on it work as on any tip;
  - lives in memory: it replaces the card until it stops being true or the page reloads; then
    the tip of the day, if any, is back;
  - when nothing is left: a card says so and links to Tips and tricks.
  It works when tips are off in Settings too: asking is an explicit request.
